# RankLab
## Exposure-Aware Two-Stage Recommendation, Learning-to-Rank, and Counterfactual Evaluation

**Document type:** Codex-ready implementation handover  
**Target outcome:** A technically defensible, non-generic Data Science / ML recommendation project suitable for DS, Applied Scientist, ML Engineer, Ranking, Personalization, and Analytics roles  
**Core problem:** Build a realistic retrieval → ranking recommender system from biased implicit-feedback logs, quantify exposure bias using randomized intervention data, and evaluate debiasing / off-policy estimators under controlled real-world benchmarks  
**Primary dataset:** KuaiRand-Pure  
**Scale extension:** KuaiRand-1K  
**Counterfactual/OPE validation dataset:** Open Bandit Dataset (OBD) / Open Bandit Pipeline (OBP)  
**Optional large-catalog extension:** Amazon Reviews 2023  
**Core models:** Popularity, BPR-MF, Two-Tower Retrieval, LightGBM LambdaRank  
**Core DS methods:** temporal evaluation, density-ratio / importance weighting, calibration, bootstrap uncertainty, subgroup/cohort analysis, counterfactual/off-policy evaluation, multi-objective re-ranking  
**Serving simulation:** FAISS candidate retrieval + batch ranker  
**Recommended stack:** Python, PyTorch, pandas/polars, LightGBM, FAISS, scikit-learn, Hydra, PyArrow, Streamlit, OBP optional  
**Primary research theme:** Recommendation quality measured against randomized exposure, not only biased historical logs

# 0. Executive Summary

RankLab is an end-to-end recommendation and ranking research system designed to look much closer to a real personalization stack than a standard student recommender.

The system should implement:

```text
historical user interactions
          ↓
user/context representation
          ↓
candidate retrieval
(two-tower embeddings + FAISS)
          ↓
100–500 candidates
          ↓
feature enrichment
          ↓
learning-to-rank
(LightGBM LambdaRank)
          ↓
optional exposure-aware weighting
          ↓
top-K recommendations
          ↓
accuracy + calibration + diversity + bias + counterfactual evaluation
```

The project is deliberately **not**:

```text
MovieLens + matrix factorization + RMSE
```

and it is not merely:

```text
train neural recommender -> report Recall@10
```

The central research problem is **exposure bias**.

In ordinary recommendation logs, a user's feedback is observed only for items the previous recommender chose to expose. This makes the data selection-biased: popular/high-ranked items are observed frequently while many other items receive little or no feedback.

KuaiRand is unusually useful because it includes both:

1. interactions generated by the standard recommendation system, and
2. interactions resulting from random item interventions inserted into the feed.

For KuaiRand-Pure, the official dataset documentation reports roughly:

```text
27,285 users
~7.5K candidate-pool items
1.44M standard-policy interactions
1.19M random-policy interactions
30 user features
62 item features
12 feedback signals
timestamps
```

This makes it possible to ask a serious DS question:

> Does a recommender that looks strong on standard logged interactions remain strong when evaluated on randomly exposed interactions, and can explicit debiasing reduce that evaluation gap?

The initial project should use **long-view** as the primary binary engagement outcome because it has a consistent dataset-defined interpretation across UI settings. Other signals such as click, like, follow, comment, forward, and profile entry can be analyzed as secondary outcomes.

The system should have four main model families:

```text
Popularity / heuristic baseline
BPR Matrix Factorization
Two-Tower Retrieval
Two-Tower Retrieval + LambdaRank re-ranker
```

Then compare:

```text
naive training on standard logs
vs
exposure-aware / randomized-target weighted training
```

The strongest result is not necessarily a large raw NDCG improvement.

A strong result could instead be:

> “Standard-log evaluation changed the apparent ranking of recommendation models; randomized-exposure evaluation revealed a measurable generalization gap, and exposure-aware weighting reduced that gap while preserving top-K relevance.”

That is a much more defensible and interesting project than simply claiming a neural recommender beats collaborative filtering.

A second, isolated **Open Bandit Dataset** module should validate off-policy estimators where logging propensities are actually known. This is important because KuaiRand's randomized logs are excellent for exposure-bias analysis, but the standard recommendation policy's exact action propensities are not provided in a form that should be casually invented.

Therefore:

- **KuaiRand:** main recommendation + randomized evaluation + exposure-debiasing project.
- **OBD/OBP:** rigorous IPS / SNIPS / Direct Method / Doubly Robust off-policy estimator benchmark.
- **KuaiRand-1K:** optional large-catalog retrieval scaling experiment.
- **Amazon Reviews 2023:** optional e-commerce-scale generalization, not required for V1.

# 2. Research Questions

The final implementation and report should answer the following.

## RQ1 — Exposure-bias evaluation gap

How different are model rankings and absolute recommendation metrics when evaluated on:

```text
standard recommendation logs
vs
randomly exposed KuaiRand interactions?
```

## RQ2 — Two-stage architecture

Does:

```text
Two-Tower retrieval + LambdaRank
```

improve ranking quality relative to:

```text
popularity
BPR-MF
Two-Tower retrieval score only
```

?

## RQ3 — Exposure-aware training

Can reweighting standard-policy training examples toward the randomized-exposure distribution improve performance on randomized interactions?

## RQ4 — Popularity concentration

Do models with stronger NDCG/Recall increase recommendation concentration toward highly exposed/popular items?

## RQ5 — User/item cohorts

Where do improvements come from?

Analyze:

- low-history vs high-history users,
- rare vs popular items,
- new vs established items,
- user activity groups,
- scenario/tab.

## RQ6 — Calibration / diversity

Can a lightweight post-ranking step improve category calibration or catalog coverage with limited relevance loss?

## RQ7 — Off-policy evaluation

On Open Bandit Dataset, how accurately do:

```text
Direct Method
IPS/IPW
self-normalized IPS
Doubly Robust
```

estimate the value of a target recommendation policy compared with known-policy ground truth?

## RQ8 — Retrieval scalability

What is the recall–latency trade-off between:

```text
exact dense retrieval
vs
FAISS approximate retrieval
```

on a larger candidate catalog?

# 3. Claim Boundaries

The implementation must be careful with causal/counterfactual language.

## Allowed claim

> “Used randomized-exposure interactions to evaluate recommendation models under substantially reduced exposure bias.”

## Allowed claim

> “Implemented importance weighting to shift standard-log training toward the randomized-exposure feature distribution.”

## Allowed claim

> “Benchmarked IPS/SNIPS/DR off-policy estimators on Open Bandit Dataset, where logging propensities are available.”

## Not allowed

> “Recovered true user preferences.”

Random exposure still measures user behavior under a specific interface, time, policy environment, and candidate pool.

## Not allowed

> “Computed exact IPS for KuaiRand's standard recommender.”

Do not claim exact propensity scoring unless the required logging probabilities are actually provided.

## Not allowed

> “Offline uplift proves an online CTR increase.”

No production A/B test is being conducted.

# 9. Leakage Rules

These are non-negotiable.

## Rule 1

All historical aggregate features used for an interaction at time `t` must use data strictly earlier than `t`.

## Rule 2

Do not compute:

```text
video popularity
user category affinity
creator affinity
engagement rate
```

using future rows.

## Rule 3

Do not use `video_features_statistic.csv` blindly.

Some provided statistical video features may summarize data over periods that overlap evaluation time.

Audit their time semantics first.

If a feature's timestamp provenance cannot be established, exclude it from the primary leakage-safe experiment and use it only in a clearly labeled relaxed-feature ablation.

## Rule 4

Randomized test interactions must never contribute labels to training.

## Rule 5

No candidate negative should be sampled from a future known positive for the same user if that would create label leakage in a temporal setup.

# 15. Baseline 0 — Global Popularity

Score items by historical long-view rate / exposure-adjusted count computed only from past data.

Implement:

```text
popularity by exposure count
smoothed long-view rate
```

Recommended smoothed rate:

```text
(score positives + alpha * global_rate) / (exposures + alpha)
```

This avoids extreme rates for low-count items.

# 16. Baseline 1 — BPR Matrix Factorization

Implement or wrap a correct BPR-MF baseline.

BPR directly optimizes pairwise ranking from implicit feedback.

Positive:

```text
long_view = 1
```

Negative sampling options:

```text
uniform unobserved
exposed-but-not-long-view
mixed
```

Primary recommendation:

Use **exposed-but-negative items when possible** for training comparisons because treating every unobserved item as a true negative is problematic under exposure bias.

For each positive standard-log interaction:

```text
sample negatives from items exposed to the user in nearby history/window with long_view=0
```

If insufficient, backfill with popularity-aware unobserved negatives.

Log negative source.

# 20. Two-Tower Training Objective

Primary:

```text
in-batch softmax / sampled-softmax contrastive retrieval loss
```

For batch size `B`, each user-context embedding's observed positive item is a positive; other batch items become negatives after false-negative filtering where feasible.

Concept:

```text
L = -log exp(s(u,i+)/tau) /
         sum_j exp(s(u,j)/tau)
```

Make temperature configurable.

# 21. Negative Sampling

Compare:

## A — Random negatives

Sample from catalog.

## B — Popularity negatives

Sample proportional to exposure/popularity.

## C — Hard negatives

Retrieve top-scoring items not observed as positive.

## D — Exposed negatives

Items actually exposed to the same user/context but without long view.

The key experiment:

```text
random
vs
exposed/mixed
```

because unobserved items are not necessarily disliked.

---

# 22. Hard-Negative Mining

After initial model training:

1. build item embeddings,
2. retrieve top-N candidates for training contexts,
3. remove known positives,
4. select top false candidates as hard negatives,
5. fine-tune.

Do not repeatedly mine negatives every minibatch in V1.

One offline hard-negative refresh is sufficient.

# 33. Exposure-Aware Debiasing Strategy

Do not invent exact standard-policy propensities.

Instead implement **randomized-target density-ratio weighting**.

Goal:

Reweight standard-policy training examples so their feature distribution better matches the randomized-exposure distribution.

---

# 34. Domain Classifier

Construct dataset:

```text
standard exposure -> domain label 0
random exposure   -> domain label 1
```

Use only variables known at exposure time:

```text
user features
item features
context/time
```

Do **not** include outcome feedback such as `long_view`.

Train:

```text
logistic regression
or
LightGBM classifier
```

Primary: logistic regression for interpretable stable density-ratio estimation.

Secondary: LightGBM.

---

# 35. Density Ratio

Let:

```text
D=1 random exposure
D=0 standard exposure
```

Estimate:

```text
q(x) = P(D=1 | x)
```

Convert classifier odds to an importance ratio adjusted for domain sampling priors:

```text
w(x) ∝ p_random(x) / p_standard(x)
```

If the domain-classifier training set intentionally balances domains 50/50:

```text
w(x) = q(x) / (1 - q(x))
```

up to the known sampling-prior correction.

If domains are sampled in natural proportions, include the prior correction explicitly.

Implement the derivation in code comments and report.

---

# 36. Weight Stabilization

Raw importance ratios can be unstable.

Compare:

```text
unweighted
raw weights
clipped weights
self-normalized weights
```

Possible clipping:

```text
1st–99th percentile
or
max weight = 10
```

Do not choose clipping based only on final test performance.

Use validation/randomized-validation subset.

Report:

```text
weight mean
weight std
max
effective sample size
```

Effective sample size:

```text
ESS = (sum w)^2 / sum(w^2)
```

The final project should be described as:

> **A two-stage personalization system combining neural candidate retrieval and learning-to-rank with randomized-exposure evaluation, exposure-aware reweighting, cohort analysis, and off-policy policy-value benchmarking.**

```text
biased historical recommendation logs
             ↓
leakage-safe temporal features
             ↓
Two-Tower retrieval
             ↓
FAISS candidates
             ↓
LambdaRank
             ↓
standard-log evaluation
          ↙       ↘
randomized exposure   popularity/cohort analysis
          ↓
exposure-aware weighting
          ↓
robustness comparison
          ↓
independent OPE validation on real e-commerce bandit logs
```

The project is valuable because it demonstrates that a recommender is not just a predictive model.

It is a **decision system trained from selectively observed behavior**, where evaluation methodology can be as important as model architecture.
